# Интеграция EKT Match

## Компоненты

| Папка | Ответственность | Точка входа |
|---|---|---|
| `frontend/` | Витрина, чат, карточки, подтверждение, корзина | `src/main.tsx` |
| `backend/` | Поиск, условия покупки, сессии, корзина, адаптеры | `src/index.js` |
| `data/` | Общий локальный каталог | `catalog.json` |
| `docs/` | Контракты и проверочные сценарии | Этот документ |
| `deploy/` | Сборка итогового контейнера | `Dockerfile` |
| `scripts/` | Совместный запуск двух процессов разработки | `dev.mjs` |

Команды описаны в [README](../README.md). В разработке Vite проксирует `/api`
в Express. В собранном режиме Express обслуживает API, статические файлы и
HTML для `/cart`: UI и API доступны с одного адреса. Неизвестные `/api/*`
возвращают JSON с HTTP 404, а не HTML интерфейса.

Docker использует тот же собранный режим: один контейнер, один порт,
относительный адрес `/api`. `compose.yaml` передаёт настройки при запуске,
а `deploy/Dockerfile` отдельно собирает Frontend и копирует готовые файлы
в образ с Backend. `GET /api/health` проверяет готовность без внешних API.
Запуск и размещение описаны в [deployment.md](deployment.md).

## Контракты

[Каталог](../data/catalog.json) сохраняет формат Data-команды. Нормализация
выполняется один раз при загрузке Backend:

| Исходные данные | API | Карточка UI |
|---|---|---|
| `sku` | `sku` | Идентификатор и артикул |
| `poles: 3` | `poles: 3` | `3P` |
| `amps: 16`, `curve: "C"` | Те же поля | `C16` |
| `breakingCapacity: 15` | `breakingCapacityKa: 15` | `15 kA` |
| `price: 7900`, `currency: "KZT"` | `priceKzt: 7900` | `7 900 ₸` |
| `stock: 12` | `stock: 12` | Остаток 12 шт. |

Для запроса по артикулу API также возвращает `quantity`, чтобы сохранить
количество даже у товара с неполными техническими характеристиками. Дополнение
не меняет существующие поля. Полный контракт: [backend-api.md](backend-api.md).

## Сессия и подтверждение

1. Клиент получает `sessionId` через `POST /api/session`, сохраняет его в
   `sessionStorage` и передаёт `X-Session-Id` в поиске и корзине.
2. Одновременные стартовые запросы используют одну операцию создания сессии.
3. Поиск и нажатие «Выбрать» не вызывают `POST /api/cart`.
4. Для выбранных SKU и количества клиент создаёт `confirmationId`. После
   явного подтверждения отправляет его вместе с `confirmed: true`.
5. UI обновляет корзину только после успешного ответа. При потере ответа
   повтор использует тот же `confirmationId` и не добавляет товар второй раз.
6. Перезапуск Backend очищает сессии и корзины. После HTTP 401 клиент создаёт
   новую сессию и повторяет отклонённый запрос один раз.

Backend заново проверяет SKU, количество и остаток. Ошибки валидации или
превышение остатка не меняют корзину; UI показывает ошибку в подтверждении.
Новые технические запросы имеют приоритет над запомненным товаром, а вопрос
«А сертификат есть?» использует контекст сессии.

## Проверка общего проекта

```sh
npm run setup
npm test
npm run build
npm run dev
```

Для собранного режима остановите dev и выполните `npm start`. Оба режима
поддерживают главный запрос из [demo-catalog.md](demo-catalog.md), переход
в `/cart` и обновление этой страницы.

Проверки находятся в `backend/test/api.test.js`, `frontend/src/App.test.tsx`
и `frontend/src/lib/api.test.ts`. Используются настоящий Express и общий
каталог. Потеря ответа после записи в корзину эмулируется на транспорте,
чтобы проверить повторную доставку подтверждения.

## Offline

Основной сценарий не использует внешние сервисы. OpenAI и API партнёра вызываются
только в `live` с соответствующими настройками. Отдельного seed-кэша ответов
в файле нет: все десять demo-запросов разбираются локально. Кэш OpenAI хранится
в памяти процесса. Условия покупки читаются из локального снимка с `sourceUrl`
и не обновляются при запуске. Перед реальным использованием снимок нужно
сверить с источником.

OpenAI получает только текст текущего запроса и схему технических параметров.
Ответ проверяется через Zod, затем передаётся существующему поиску по каталогу.
Товары, цены и остатки берутся из каталога. Ключ остаётся в окружении Backend.
